# 车辆配钥匙授权服务（Go 参考实现）

针对"维修站流出的诊断设备和账号在停车场几分钟配上新钥匙"这类攻击，重写配钥匙的授权链路。

核心判断：**被盗的恰恰是设备和账号，所以任何"验证设备可信 / 验证账号可信"的方案都挡不住本案**。信任锚必须下沉到两个互相独立、维修站伪造不了、也无法良好伪造的物理事实：

1. **车在这儿** —— 由车辆自己的安全元件（HSM）签名。私钥出厂烧录，永不出车。停车场里没有这辆车，就没有这个签名。
2. **车主本人在场** —— 由车主已登记的手机签名，并且**由车辆**出具近距离证明（BLE/UWB 往返时延），而不是由手机或维修站自证。

维修站能做的只剩"把授权书递给车"，它造不出、也改不宽授权书。

---

## 三种角色，三种能力

| 角色 | 能证明什么 | 不能证明什么 |
|---|---|---|
| 诊断设备 / 技师账号 | 这是某台站内设备 | 人在场、车在场、车主同意 |
| 维修站后台系统 | 这辆车今天进过本站某工位（工单） | 车主同意 |
| 车辆 HSM | 这辆车此刻就在诊断口上 | 车主是谁 |
| 车主手机 | 车主点过"同意" | 手机是否真在车旁 |

**关键设计：** 设备签名只用来路由和限流，**从不作为授权依据**。本案里攻击者的设备签名是完全合法的。

---

## 授权是怎么判定的

`internal/policy` 是一个纯函数：相同输入永远得到相同结论，不需要读时钟、不读随机数、不做 IO。任何一次判定都能在几年后从审计日志里精确复现——这既是为了追责，也是为了排查 bug。

### 低风险：车还有钥匙时新增一把

必要条件（缺一不可）：

- 车辆 HSM 对本次会话挑战签名（车在场）
- 车辆报告**某个已有钥匙插进去并通过了密码挑战**（不是"无线电扫到"）
- 维修站后台有该 VIN 的、未过期的、未关闭的进站工单（车在站里）
- 车主手机签名同意，且**车辆出具近距离证明**

三种结果：

- 车主在场 + 手机贴着车 → `low`，永久钥匙，无附加条件（这是绝大多数正常业务，不打折）
- 车主远程同意 → `elevated`，需要**另一名技师用另一台设备**现场见证；钥匙是**临时钥匙**，车主可在撤销窗口内单方面撤销
- 完全没有车主同意 → 直接转高风险路径（见下）

### 高风险：钥匙全丢了 / 首次绑定

- 车仍然必须证明自己在场（这条从不豁免）
- 车辆若报告还有活钥匙，就拒绝"全丢"声明，要求改走新增
- 路径 A：车主带着已登记手机、贴着车同意 → 临时钥匙，无需冷却期
- 路径 B：车主连手机都没有 → 必须①独立身份核验机构的签名声明 ②第二名技师见证 ③**冷却期**内所有登记联系人收到告警、任何人可一票否决
- 路径 B 的钥匙：**每次启动都要求车主手机在旁**，且**有使用次数上限**

### 防滥用

- 每车每日高风险次数上限、每站每日上限（防被攻陷的站"刷车"）
- 车辆状态为"已报失"时，任何配钥匙都拒绝
- 维修站被停权时，即使设备密码学上完全有效也拒绝
- 近期过户的车辆，高风险操作强制走冷却期 + 见证

## 弱网 / 地下车间

网络差不是安全与可用性的取舍点：

- **正常新增钥匙可以完全离线完成。** 车辆在出厂时预置了策略；维修站后台提前签发、手持设备缓存的**进站票**让车辆在无网时也能验证"车确实进了授权工位"。低风险 + 已有钥匙在车上 + 车主手机贴近同意 → 车辆自签 `LocalGrant`。网络恢复后服务端补记并交叉校验。
- **高风险操作不提供离线路径。** 这是有意的。丢光钥匙且在弱网地下室里，应该等网络恢复或走到有信号的地方——这不是"繁琐"，这是该慢的时候慢。

`sess` 打开时的挑战带 10 分钟有效期，证明带 5 分钟，且绑定会话、VIN、用途、钥匙槽位、新公钥和双方 nonce。录下来的旧证明换到新会话里立刻失效（有测试覆盖）。

---

## 为什么不用"视频通话 / 人脸识别"做主判定

会建议用，但不作为**唯一**锚点：

- 视频里的"车主"可以是同伙；维修站内鬼可以找人演戏
- 人脸库本身是集中攻击目标
- 但它适合作为**路径 B 身份核验**的一种实现，配合冷却期和联系人否决使用

同理 GPS 只做**否定性**佐证：位置明显不符 → 拒绝；位置相符 → 几乎不加分（GPS 可伪造）。

## 审计

`internal/audit` 是哈希链：每条记录包含前一条的哈希。删改任何一条，从该点起链断裂。生产环境应把链头定期锚定到一次写存储（S3 Object Lock / 透明日志）。**被拒绝的尝试也全部记录**——调查时最有用的是失败记录。

## 防止服务端本身被攻陷后放大权限

Grant 由服务端签发，但**车辆自己**用出厂预置的授权公钥验签。服务端私钥在 HSM 里。也就是说：

- 手持设备改不了 Grant（验签失败，有测试）
- 服务端主机被完全攻陷，没有 HSM 也签不出车辆认的 Grant
- `Constraints`（临时性、每次启动需车主在旁、次数上限、撤销截止）写进签名体，车辆强制执行，不是"建议"

---

## 这个方案挡不住什么（必须知道）

1. **车主的手机和本人一起被胁迫。** 物理胁迫没有纯技术解；联系人否决和冷却期只能争取时间。
2. **厂端 HSM / 授权私钥泄露。** 这是整个体系的根，必须独立加固、分离权限、定期轮换。
3. **维修站后台系统被完全攻陷**，能伪造工单——但工单只证明"车在站里"，仍拿不到车辆 HSM 签名和车主近距离证明。
4. **车辆 HSM 固件被攻破。** 与车辆信息安全团队联合威胁建模，不在本服务范围内。
5. **合法的远程同意被社会工程骗取**（"帮我点一下同意"）。已通过"远程同意 = 临时钥匙 + 可单方面撤销 + 需见证"把损失限制在可撤销、可追溯。
6. 老车型没有联网 HSM / 近距离能力。需要分阶段：先用后台工单 + 双人见证 + 冷却期兜底，逐步铺开硬件能力。

## 代码结构

```
internal/
  canon/      确定性 JSON 编码（签名可复现的前提）
  vcrypto/    Ed25519 + 域分离 + 常量时间比较
  model/      领域类型
  protocol/   所有签名消息；每条都绑定会话/VIN/用途/密钥/nonce/有效期
  policy/     纯函数判定引擎（无 IO、无时钟、可复现）
  service/    编排：验签、策略、签发 Grant、恢复流程、冷却期与否决
  audit/      哈希链审计日志
  store/      内存参考实现（生产需事务化 + 持久化）
  api/        HTTP 薄封装（自身不做任何授权判断）
  sim/        端到端场景测试用的完整世界
  scenariotest/  按真实攻击命名的场景测试
cmd/
  authz/      服务入口
  demo/       跑一遍全部场景并打印判定与理由
```

## 运行

```bash
go test ./...          # 全部场景与单元测试
go run ./cmd/demo      # 打印正常业务与各类攻击的判定结果
go run ./cmd/authz     # 需要 VKZ_ISSUER_KEY_ID 与 VKZ_ISSUER_PRIVATE_KEY_HEX
```

`demo` 的输出是可直接用于评审和培训的验收材料：每个攻击都打印出**具体缺哪一个物理事实**，而不是笼统的"拒绝"。
